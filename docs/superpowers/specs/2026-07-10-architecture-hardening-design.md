# 闲鱼购系统渐进式架构治理设计

## 1. 背景与目标

当前系统采用 React/Vite 前端、FastAPI 后端、SQLite 数据库、Node 邮件服务和 Docker Compose 本地部署。系统已具备交易、客户、质保、售后、财务、闲鱼订单与商品同步等能力，并建立了较完整的前后端自动化测试。

本次治理不增加新业务功能，不推倒重写。目标是在完整保留当前工作区成果、现有业务数据、界面和操作流程的前提下，降低数据不一致、数据库升级失败、模块耦合和故障定位困难等风险。

## 2. 已确认约束

- FastAPI + SQLite 是唯一业务数据源。
- 未来 12 个月保持单机、单用户、本地 Docker 部署。
- 不引入登录权限、公网部署、微服务、消息队列、Redis 或新的数据库产品。
- 现有业务数据和功能必须完整保留，不接受清库重建。
- 每个改造阶段必须可备份、可验证、可回滚。
- 当前未提交改动均视为有效成果，后续只做增量修改，不覆盖或回退。
- 闲鱼同步继续遵守低频、串行、遇认证或风控即停止的安全边界。

## 3. 目标架构

系统继续采用模块化单体架构：

1. React 前端负责界面、交互状态和 API 调用，不保存业务主数据。
2. FastAPI 是唯一业务入口，按 `router -> service -> model/database` 分层。
3. SQLite 是唯一持久化数据库，使用 Alembic 管理结构版本。
4. 闲鱼订单和商品镜像属于外部源数据层；交易、财务、质保和售后属于内部业务投影层。
5. Node 邮件服务保留为独立适配器，本轮不重写。
6. Docker Compose 继续作为唯一推荐部署入口，所有端口默认只绑定回环地址。

## 4. 数据流与一致性

### 4.1 业务数据

所有业务查询和写入统一通过后端 API。前端 Dexie 业务表不再作为运行时数据源。迁移采用两步法：先停止业务表写入并保留只读兼容，再确认后端数据完整后移除业务表定义和迁移入口。浏览器只保留主题、导航折叠状态、后端地址等非业务配置。

### 4.2 闲鱼同步

闲鱼响应必须先写入订单或商品镜像，再幂等投影到内部业务表。投影在单个数据库事务内完成，并遵守以下规则：

- 平台字段与人工字段分离。
- 自动同步不得覆盖成本、模板选择、推荐关系、备注、附件和人工售后内容。
- 同一账号和平台对象通过唯一约束实现幂等。
- 外部响应解析失败时保留既有业务数据，不产生部分投影。
- Cookie、Token、密钥和完整原始响应不得出现在日志或 API 错误中。

## 5. 数据库版本与恢复

### 5.1 Alembic 基线

引入 Alembic 后，先创建与当前生产 SQLite 结构等价的基线版本。已有数据库通过校验后标记到该版本；新数据库从基线迁移创建。随后将 `create_all` 和 `_ensure_sqlite_columns` 中的结构变更迁入显式版本文件。

应用启动时只执行版本检查。数据库版本落后、超前或迁移失败时，后端拒绝提供业务写入，不静默修改结构。

### 5.2 备份与回滚

每次结构迁移前执行 SQLite 一致性备份，并保留业务 JSON 导出作为逻辑备份。备份文件、数据库文件和密钥均不进入 Git。恢复演练必须验证：

- SQLite 完整性检查通过。
- 核心表记录数与迁移前一致。
- 加密字段仍可由原密钥读取。
- 交易、客户、质保、售后和闲鱼投影关系可查询。

迁移失败时停止新版本，恢复数据库文件并回退到上一个容器版本；禁止在未知结构上继续运行。

## 6. 模块边界

### 6.1 后端

- router 只负责请求校验、依赖注入和响应转换。
- service 负责业务规则、事务边界和跨模型协作。
- model 只表达持久化结构和约束。
- 将集中式 `schemas.py` 按业务域拆分，但保持现有导入兼容，避免一次性大改。
- 将 `routers/settings.py` 中的商品、财务、审计和迁移接口逐步移动到各自路由模块。
- 统一业务异常类型和 API 错误格式，区分校验错误、业务冲突、外部平台错误和系统错误。

### 6.2 前端

- 保留现有 service API 层，并统一日期、金额和错误响应归一化。
- 大型页面按“页面容器、业务组件、业务 hook”拆分。
- Zustand 只保存真正跨页面的 UI 状态；服务端数据由页面或业务 hook 管理。
- 拆分不得改变现有路由、页面布局、字段含义和操作路径。
- 后端原始异常不直接显示，统一转换为稳定、可操作的中文提示。

## 7. 性能与可观测性

当前规模下不引入缓存基础设施。优化顺序为：

1. 为高频筛选、外键关联和唯一幂等字段补齐索引。
2. 列表 API 统一分页、排序和最大页大小。
3. 统计接口在数据库侧聚合，避免前端拉取全量记录计算。
4. 前端路由懒加载，图表和大型弹窗按需加载。
5. 为后端请求生成关联 ID，日志记录模块、结果、耗时和脱敏错误类型。
6. 健康检查区分进程存活与数据库可用性，但不暴露内部路径和配置。

## 8. 错误处理

- 参数错误返回稳定的字段级说明。
- 业务冲突返回可识别错误码，例如重复同步、状态不允许或数据版本冲突。
- 闲鱼认证、验证码和风控错误立即熔断，不自动绕过。
- 数据库迁移和完整性错误阻止业务服务启动。
- 前端保留用户已输入但尚未提交的表单内容，允许修正后重试。
- 所有失败路径不得记录或返回凭证、密钥和未经脱敏的外部响应。

## 9. 测试与验收

每个阶段必须同时满足：

- 后端完整 pytest 测试通过。
- 前端 Vitest 测试和 TypeScript/Vite 构建通过。
- 新增迁移具备“空数据库升级”和“现有数据库升级”测试。
- 备份恢复演练通过，迁移前后核心表数量和关键关系一致。
- 重复闲鱼同步不产生重复镜像、交易、售后或事件。
- Docker Compose 重建后三个服务正常，前端和健康检查可访问。
- Git diff 仅包含本阶段相关改动，不夹带凭证、运行数据或无关重构。

## 10. 实施分期

### 阶段 0：保护当前基线

记录工作区状态，完成测试、构建、容器健康检查和数据库备份恢复演练。此阶段不改变业务行为。

### 阶段 1：数据库迁移体系

引入 Alembic、建立等价基线、接管手写结构变更，并增加版本检查与迁移测试。

### 阶段 2：单一数据源收敛

确认全部 service 已使用后端 API，停止 Dexie 业务写入，验证数据一致后移除业务数据库兼容代码。

### 阶段 3：后端模块治理

按业务域拆分 schema 和集中路由，统一异常与事务边界；保持 API 合同不变。

### 阶段 4：前端模块治理

优先拆分 `Settings.tsx` 和 `OrderSync.tsx`，再处理其他大型页面；保持页面行为不变。

### 阶段 5：性能与运维闭环

补齐索引、分页、聚合、路由懒加载、请求关联 ID、健康检查和部署验证文档。

每个阶段单独实施、测试和提交。只有当前阶段验收通过，才进入下一阶段。

## 11. 非目标

本次不实现多用户、权限管理、云端同步、移动端重做、数据库替换、微服务拆分、异步消息系统、闲鱼风控绕过或新业务功能。发现相关问题时只记录，不扩大本次治理范围。

## 12. 完成标准

治理完成后应满足：

- 业务数据只有一个权威来源。
- 数据库结构变化全部可追踪、可验证、可回滚。
- 应用不会在未知数据库版本上继续写入。
- 主要业务模块边界清晰，大型页面和集中路由得到拆分。
- 现有功能、数据、路由和操作方式保持兼容。
- 完整测试、构建、备份恢复和 Docker 部署验证全部通过。
