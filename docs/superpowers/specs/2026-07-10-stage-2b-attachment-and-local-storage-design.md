# 阶段 2B：附件与本地存储收敛设计

## 目标

完成前端业务 IndexedDB 的最终退出：附件由 FastAPI + SQLite 统一存储和读取；备份密码加密保留在浏览器端，但与旧业务字段加密彻底拆分；删除 Dexie、浏览器主密钥库和 fake-indexeddb。

## 当前事实与约束

- 后端已有 `attachments` 表、BLOB 字段、Alembic 基线，以及 JSON 备份导入导出支持，缺少在线附件 API。
- 前端仅 `attachmentService.ts` 仍直接使用 Dexie；`crypto.ts` 中仅备份密码加密仍有有效调用，字段加密和 IndexedDB 主密钥逻辑已经失效。
- 2026-07-10 切换前只读核对结果：后端附件数为 0，交易附件引用数为 0，售后附件引用数为 0；因此当前真实后端数据不存在需要迁移的附件或悬空附件引用。
- 系统继续保持单机、单用户、本地 Docker、SQLite 唯一业务数据源，不引入对象存储、权限体系或分布式组件。

## 方案比较

### 方案 A：继续保留 Dexie 仅存附件

改动最少，但业务数据仍分裂在浏览器与后端，换浏览器或清理站点数据会丢附件，也无法由服务器备份完整保护。不采用。

### 方案 B：SQLite BLOB + 后端附件 API

复用已有模型、迁移和备份链路，只补齐上传、批量元数据、内容读取与删除接口。符合当前部署规模，数据一致性和运维成本最好。采用。

### 方案 C：文件系统或对象存储

更适合大量文件或多实例部署，但会引入路径一致性、孤儿文件、独立备份和部署配置问题，超出当前需求。不采用。

## 架构设计

### 后端附件边界

新增独立附件服务与路由：

- `POST /api/attachments`：接收 multipart 单文件，服务端再次校验 5 MB 上限与 JPG/PNG/WebP/GIF MIME，写入 SQLite BLOB，返回元数据。
- `POST /api/attachments/batch`：接收附件 ID 数组，按请求顺序返回仍存在的附件元数据，不返回二进制。
- `GET /api/attachments/{id}/content`：以内联响应返回图片内容，并设置正确的 Content-Type 与安全文件名。
- `DELETE /api/attachments/{id}`：删除附件；不存在时返回 404。

附件表继续使用现有 Alembic 结构，不新增数据库迁移。上传校验必须以后端为准，前端校验仅用于即时反馈。

### 前端附件边界

`attachmentService.ts` 改为后端 API 适配器：

- 上传使用 `FormData`，不再构造或持久化浏览器 Blob。
- 批量加载只获取元数据；图片缩略图和预览直接使用后端内容 URL。
- 删除调用后端 DELETE。
- `Attachment` 前端类型移除 `blob`，保留 id、名称、MIME、大小和创建时间。

`apiClient.ts` 增加受控的 multipart 请求能力，并复用统一的后端地址和错误转换；内容 URL 由同一模块生成，避免附件服务自行拼接地址。

现有表单仍保存字符串附件 ID，交易和售后 schema 不变。

### 浏览器加密收敛

新增 `backupCrypto.ts`，只保留以下无状态密码派生能力：

- PBKDF2-SHA256 派生密钥；
- AES-256-GCM 加密/解密完整 JSON 备份；
- `backup:v1:` 格式识别。

删除旧 `crypto.ts` 中字段加密、解密、IndexedDB 主密钥和 `enc:v1:` 兼容代码。设置页与导入导出模块统一改用 `backupCrypto.ts`。

### Dexie 退出

附件切换并验证后删除：

- `src/db/index.ts`；
- 未被使用的 `tests/helpers.ts`；
- 测试初始化中的 fake-indexeddb 注入；
- `dexie` 与 `fake-indexeddb` 依赖。

架构边界测试扩展为：生产源码不得导入 `@/db`、不得出现 Dexie 或业务 IndexedDB 主密钥库；`package.json` 不得声明 Dexie/fake-indexeddb。

## 数据流

上传流程：浏览器选择文件 → 前端快速校验 → multipart 上传 → 后端权威校验 → SQLite BLOB 写入 → 返回附件 ID → 交易或售后记录保存该 ID。

展示流程：页面读取交易/售后附件 ID → 批量获取元数据 → `<img>` 使用后端内容 URL → 后端从 SQLite 流式返回图片。

备份流程保持不变：后端导出时将 BLOB 转 Base64；浏览器可选用密码加密整个 JSON；恢复时浏览器解密后交给后端导入。

## 错误处理与安全

- 服务端拒绝空文件、超限文件和非允许 MIME，返回明确 400/413。
- 不信任原始文件路径，只保留基础文件名并限制长度；内容响应使用 inline，避免任意路径写入。
- 批量查询忽略已不存在 ID，与当前 Dexie `bulkGet` 后过滤行为一致。
- 上传成功但业务表单取消时可能留下孤立附件，这是既有行为；本阶段不增加后台清理任务，避免扩大范围。
- 当前真实后端附件与引用均为 0，因此无需一次性旧附件迁移脚本；切换前的已验证 SQLite 备份继续作为回滚点。

## 测试与验收

- 后端路由测试覆盖：合法上传、内容一致、批量元数据顺序、删除、超限、非法 MIME、404。
- 前端服务测试覆盖：multipart 上传、批量元数据日期归一化、内容 URL、删除与错误传播。
- 备份加密测试覆盖：往返解密、随机密文、错误密码、损坏格式和空密码。
- 架构边界测试确认前端无 Dexie、无业务 IndexedDB、无旧字段加密符号。
- 全量验收：前端测试、TypeScript、生产构建、后端测试、Docker 重建、附件真实上传/读取/删除冒烟、Alembic current=head、备份复验。

## 非目标

- 不引入 MinIO、S3、文件系统存储或 CDN。
- 不实现附件缩略图生成、病毒扫描、内容哈希去重或孤儿定时清理。
- 不改变交易与售后附件 ID 字段格式。
- 不修改现有 JSON 备份文件格式版本。
