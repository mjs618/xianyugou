# 阶段 3C：闲鱼订单解析边界设计

## 目标

从 556 行的 `app/services/xianyu/order_service.py` 中抽离纯订单载荷解析职责，建立可独立测试的 `order_parser.py`，同时保持同步入口、数据库写入、状态投影、鉴权重试、API 与 OpenAPI 契约不变。

## 当前状态

- `order_service.py` 同时承担 MTOP 拉取、响应结构兼容、订单字段解析、平台状态映射、数据库镜像、交易投影、账号锁、Cookie 刷新和同步日志记录。
- 字段与时间解析是无数据库、无网络副作用的纯逻辑，但与同步编排混在同一文件中。
- `item_service.py` 为 368 行，也包含类似解析逻辑；本阶段先治理更大的订单服务，不同时扩大到商品服务。
- 现有订单镜像、生命周期投影和路由测试已经保护主要同步行为，但没有独立锁定解析模块边界。

## 方案比较

### 方案 A：只抽离订单载荷解析器

把字段提取、响应列表解析、平台状态映射和时间解析移入纯函数模块；数据库、网络与 ORM 投影仍由 `order_service.py` 负责。职责清晰、依赖单向、回归面最小。采用。

### 方案 B：同时抽离交易投影器

进一步把 `Transaction` 状态、发货时间、质保到期和版本号更新移到独立模块。边界更完整，但会移动 ORM 状态变更和领域计算，增加本阶段验证成本。不采用。

### 方案 C：拆分完整同步编排流程

把拉取、鉴权重试、镜像、投影和日志分别编排。可显著缩短主函数，但会触及事务和失败恢复语义，不适合作为第一步。不采用。

## 模块结构

新增 `app/services/xianyu/order_parser.py`，负责：

- `extract_order_no`：兼容顶层与 `commonData` 的订单号字段。
- `extract_price`：兼容顶层与 `priceVO` 的价格字段和分/元转换。
- `extract_buyer_nick`、`extract_product_name`、`extract_item_id`、`extract_order_status`：统一读取平台载荷。
- `project_transaction_status`：把平台状态映射为 `pending`、`completed`、`aftersales`、`closed` 或不投影。
- `parse_orders`：兼容现有 MTOP 响应列表路径。
- `parse_trade_time`、`extract_shipped_time`：解析 ISO、秒级和毫秒级时间。

`order_service.py` 通过显式导入使用这些函数，只保留：

- 账号级同步锁。
- 客户和商品模板查询。
- MTOP 翻页拉取。
- 订单镜像与交易投影写入。
- Cookie 刷新、账号状态和同步日志。

## 依赖规则

- `order_parser.py` 只允许依赖 Python 标准库，不导入 SQLAlchemy、FastAPI、应用模型、数据库会话、加密或 MTOP 客户端。
- `order_service.py` 可以依赖解析器；解析器不得反向依赖服务。
- 解析器不引入 dataclass、DTO 或配置对象，继续接收原始 `dict`，避免改变现有数据流。
- 原 `order_service.py` 的公开入口 `fetch_orders`、`upsert_order_mirror`、`list_order_mirrors`、`sync_orders_for_account` 与 `SyncAlreadyRunningError` 保持原路径和签名。
- 原下划线解析函数属于内部实现，不承诺兼容导出；生产代码无调用方依赖这些私有名称，原服务测试中的解析断言迁移到新解析器公共接口。

## 行为兼容

- 未携带状态的订单仍默认投影为 `completed`。
- 已付款、待发货、已发货、待收货仍投影为 `pending`；退款处理中仍投影为 `aftersales`；全额退款成功仍投影为 `closed`；待付款和关闭类状态仍不创建新交易。
- 未知状态仍不投影；中文退款处理中模糊匹配规则保持不变。
- 价格字段优先级、整数大于 1000 时按分换算的既有规则保持不变。
- 交易时间仍以完成、支付、创建等字段依次回退，全部缺失时由服务传入当前时间兜底；发货时间缺失时返回 `None`。
- MTOP 翻页大小、最大页数、后续页失败时保留已拉取数据的规则不变。

## 测试策略

新增 `test_xianyu_order_parser.py`，并把 `test_order_service.py` 中直接调用原私有解析函数的断言迁移到新解析器：

1. 在模块不存在时先以断言失败建立 RED 基线。
2. 覆盖嵌套订单号、价格、买家、商品、状态和时间解析。
3. 覆盖主要状态集合、中文退款模糊匹配与未知状态。
4. 覆盖 MTOP 多种响应列表路径。
5. 通过源码边界断言禁止解析器引入应用层和第三方依赖，并确认解析函数归属新模块。

现有订单镜像、订单生命周期投影和路由测试继续作为集成保护。完成后运行后端全量测试、前端全量测试、类型检查、生产构建和容器运行态验证。

## 实施顺序

1. 新增解析器行为与依赖边界测试，确认因模块缺失而失败。
2. 创建纯 `order_parser.py`，原样迁移并公开命名解析函数。
3. 修改 `order_service.py` 为显式导入，删除重复解析实现和状态常量。
4. 运行解析器、订单同步与路由测试，再运行全量回归。
5. 重建后端容器，验证健康、订单列表、账号列表与 OpenAPI；复验 Alembic 和备份。

## 回滚

本阶段不修改数据库、迁移、路由或前端。出现问题时回退解析器拆分提交即可恢复单文件实现，不需要数据回滚。

## 非目标

- 不拆分商品解析器。
- 不移动 ORM 交易投影逻辑。
- 不重写同步编排、鉴权重试或事务提交方式。
- 不修改平台状态集合和字段兼容规则。
- 不引入新的抽象基类、依赖注入容器或通用解析框架。

## 验收标准

- 订单解析逻辑全部归属 `order_parser.py`，且该模块只依赖标准库。
- `order_service.py` 不再定义重复解析函数，公开服务入口保持兼容。
- 新解析器测试、现有闲鱼订单测试和后端全量测试通过。
- 前端测试、类型检查和构建通过。
- 后端容器重建后关键只读端点返回 200，Alembic 与备份校验保持正常。
