# 安全优先的闲鱼订单全生命周期同步设计

## 目标

为个人卖家的本地 Docker 系统增加闲鱼订单全生命周期同步，同时将账号安全置于自动化便利性之上。系统不能承诺避免平台风控；遇到认证、验证码或风控响应时必须停止后台请求并等待人工恢复。

## 安全边界

- 自动同步默认关闭，由用户逐账号启用。
- 默认同步间隔 120 分钟，最短不低于 60 分钟。
- 单账号串行执行，同一账号不能并发同步。
- 登录失效、验证码、访问频繁或风控响应立即熔断，不自动恢复。
- 不实现代理轮换、设备伪装、验证码绕过或其他规避平台控制的能力。
- Cookie、Token、加密密钥和完整原始响应不得进入源码、镜像、日志或 API 响应。
- Web、后端和邮件服务默认只绑定 `127.0.0.1`。
- 后续若具备资质，应优先迁移到闲鱼官方授权接口。

## 分层架构

同步链路为：安全调度器 → MTOP 适配器 → 订单镜像 → 状态事件 → 业务投影。

`xianyu_orders` 保存平台订单镜像，`xianyu_order_events` 保存状态变化。交易、售后、质保和财务模块不直接解析平台响应，只消费标准化后的订单状态。平台字段与人工字段分开管理，自动同步不得覆盖成本、商品模板、推荐关系、备注、附件和人工售后内容。

## 状态映射

| 平台状态 | 内部动作 |
|---|---|
| 待付款 | 仅保存订单镜像 |
| 待发货、已付款、已发货、待收货 | 创建或更新 `pending` 交易 |
| 交易成功 | 更新为 `completed`，确认收入并开始质保 |
| 退款处理中 | 更新为 `aftersales`，创建或关联闲鱼来源售后单 |
| 部分退款成功 | 保持 `completed`，按净收入计算利润 |
| 全额退款成功 | 更新为 `closed`，净收入归零并关闭质保 |
| 未付款关闭 | 保留镜像，不进入财务统计 |

## 调度与恢复

- 普通同步最多读取最近两页；有限深度对账每天最多一次。
- 服务重启后不集中补跑错过任务，只延迟执行一次。
- 网络超时和 5xx 不立即重试，等待下一周期。
- 连续三次未知失败后暂停账号。
- 暂停后必须人工更新 Cookie、通过只读校验并点击恢复。
- 手动同步同样受并发锁、最短间隔和熔断约束。

## 当前实施顺序

1. P0 安全加固：密钥退出版本控制、本机端口绑定、错误脱敏。
2. P1 订单镜像层：数据模型、幂等 upsert、状态事件。
3. P2 业务投影：交易、退款、售后、质保和财务。
4. P3 安全调度：限频、锁、熔断、告警和人工恢复。

## 验收标准

- Git、镜像、日志和 API 响应中不存在可用密钥、Cookie 或 Token。
- 服务默认不能从局域网访问。
- 重复同步不产生重复订单、交易、售后或事件。
- 平台状态变化可追溯，人工字段不被覆盖。
- 部分退款和全额退款的净收入、利润和质保处理正确。
- 风控响应出现后不再产生后台请求。
- 自动化测试只使用固定响应样本；真实账号验证必须人工触发并限制调用次数。
