# 自动同步与迁移安全闭环设计

## 目标

审计并闭环工作区中已有的 P3 自动同步、熔断恢复和容器自动迁移改动，确保后端安全约束不可被 UI/API 绕过，真实数据库升级前必有可验证备份，同时保留现有功能和数据。

## 审计结论

- 自动同步默认关闭、账号独立周期、同账号锁、连续失败熔断和人工恢复主体实现正确。
- 暂停账号仍可直接调用订单/商品同步 API；订单同步成功还会隐式恢复账号，违反熔断边界。
- 手动订单同步未执行设计要求的最短 60 分钟限频。
- CookieCloud 刷新后的普通 MTOP 错误被统一归类为认证失败，可能错误地立即暂停账号。
- 更新普通 `invalid`/`risk` 账号的有效 Cookie 不再恢复在线，造成旧行为回归；只有 `paused` 必须显式恢复。
- 容器 entrypoint 自动迁移已有数据库，但迁移前未创建备份。
- 健康响应的既有 `service=xianyu-backend` 被无关改名，应保持兼容。
- datetime API 更新、Python 3.13 依赖升级和 Vite vendor 分块属于独立维护改动，分组验证和提交，不与安全修复混合。

## 安全门设计

- 在 `account_service` 提供暂停状态断言和手动订单同步预检。
- 订单与商品服务在创建 MTOP 客户端前强制拒绝 `paused` 账号，保证直接调用服务也无法绕过。
- 手动订单路由在进入同步服务前检查 `last_sync_at`，距上次尝试不足 60 分钟返回 HTTP 429；后台调度仍按每账号 60–1440 分钟配置判定。
- 并发锁继续由订单服务承担；限频不替代锁。
- 暂停恢复继续要求暂停后更新 Cookie，并通过本地只读格式校验。

## 状态与失败分类

- 登录失效或风控响应立即进入 `paused`。
- CookieCloud 刷新后的重试错误按其真实标志分类：`risk`、`auth_fail` 或 `unknown`。
- 未知失败累计三次暂停；成功清零计数。
- 更新 Cookie 时：`paused` 保持暂停，必须显式恢复；其他状态恢复 `online` 并清除旧错误，保持原有体验。

## 迁移前备份

- `migrate_database` 仅在“已有数据库且 current != head”时创建迁移前备份。
- 全新空数据库不创建无意义备份。
- 备份目录由数据库位置推导：`<backend-root>/backups`；容器中自然对应 `/app/backups` 挂载。
- 文件名使用 UTC 微秒时间戳，`create_backup` 继续禁止覆盖并生成 SHA-256、完整性和表计数清单。
- 备份创建或校验失败时立即终止迁移和应用启动。

## API 兼容

- 健康响应保留 `service=xianyu-backend`，新增的 `scheduler_running` 字段保留。
- 暂停账号同步返回 409；手动限频返回 429，并提供明确中文错误。
- 现有同步成功响应、账号 schema 和恢复端点保持不变。

## 测试

- 新增失败测试覆盖暂停账号订单/商品服务零网络调用、手动限频、普通账号 Cookie 更新恢复、重试错误分类。
- 新增迁移测试覆盖已有库先备份再升级、全新库不备份、备份失败阻断迁移。
- 新增健康契约测试锁定既有服务名与调度字段。
- 运行自动同步、账号恢复、迁移、前后端全量测试和构建。
- Docker daemon 可用前不启动真实容器；迁移逻辑先只在临时 SQLite 数据库验证。

## 提交边界

1. 安全调度、熔断、恢复、模型/schema/API/前端及对应测试。
2. 数据库迁移、entrypoint、Dockerfile 和迁移测试。
3. datetime 兼容修正。
4. Python 3.13 依赖锁升级。
5. Vite vendor 分块优化。

每组精确暂存，避免混合提交。

## 非目标

- 不真实调用闲鱼接口。
- 不启动或迁移当前 Docker 真实数据库，除非先确认 daemon、备份和迁移预演均通过。
- 不引入分布式调度、代理、验证码绕过或多 worker 协调。
- 不修改同步业务投影与财务口径。

## 验收标准

- 暂停账号无法通过任何订单/商品同步服务产生 MTOP 请求。
- 手动订单同步满足 60 分钟限频和并发锁。
- 自动迁移已有库前生成并验证备份，失败时数据库版本不变化。
- 所有新增与既有测试通过，提交边界清晰，无敏感数据输出。
